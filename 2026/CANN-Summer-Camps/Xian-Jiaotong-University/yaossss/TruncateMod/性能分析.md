# TruncateMod 性能分析

## 1. 测试来源

性能数据来自 CANNJudge 结果表 `核心算法性能测试-.xlsx`，共 50 个测试点；功能结果来自 `通过截图.png`。

测试目标是比较内置算子 Baseline 与 Ascend C 自定义算子的单次耗时，判定条件为：

```text
custom_time < baseline_time
```

## 4. 优化点分析

### 4.1 多核切分

Host 侧以 32 个元素为基本 Block，根据输出元素数和设备核数计算 `blockDim`，并将多余 Block 均衡分配到前若干个核。大形状用例可以同时使用多个 AI Core，降低单核串行处理时间。

### 4.2 按 dtype 选择 Tile

- FLOAT、FLOAT16、BF16 使用 6144 元素 Tile。
- INT32、INT8、UINT8 使用 4096 元素 Tile。

该策略在 UB 占用、双缓冲空间和循环次数之间取得平衡，避免统一使用过小 Tile 导致循环开销增加。

### 4.3 广播快路径

同形状输入使用连续 DataCopy；标量广播使用 Duplicate 或 FillScalar；单侧完整输入广播只对另一侧执行地址计算。只有一般广播和非连续布局才进入逐元素 Gather 路径。

### 4.4 搬运和尾块处理

32 字节对齐的数据使用 DataCopy，尾部不对齐数据使用 DataCopyPad。这样既减少对齐场景的搬运指令，又避免尾块越界访问。

### 4.5 计算路径

FLOAT 路径直接使用 FP32 计算；BF16、FLOAT16、INT32、INT8、UINT8 使用必要的转换缓冲完成 FP32 核心计算，并用 CAST_TRUNC 实现向零截断。关键向量操作之间使用 PipeBarrier 保证数据依赖。

## 5. 性能结论

当前版本在 CANNJudge 的 50 个测试点上全部通过，且所有自定义算子耗时低于 Baseline。性能瓶颈主要集中在大形状用例的内存搬运和固定启动开销，当前实现已经满足任务书要求，后续优化应以不破坏广播泛化和 dtype 精度为前提。
